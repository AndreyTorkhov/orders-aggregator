# Решение

## Что сделано

В `daily-totals` добавлены `gross`, `discount` и `net`. Поле `total` осталось равным `gross`. Фактическая оплата берётся из `amountPaid`: пересчитывать её по проценту скидки не нужно.

Оплата сохраняется в копейках через общую обработку синхронизации и вебхуков. Для этого добавлена миграция `002_amount_paid.sql`. Интерфейс `OrdersApi`, сигнатура `createContainer(db, api)` и зависимости не менялись.

## Причина расхождений у c_7

Сервис брал смещение таймзоны на текущую дату и применял его ко всем заказам. У `c_7` таймзона `Europe/Berlin`: 29 марта 2026 года она переходит с UTC+1 на UTC+2. Из-за этого часть вечерних заказов попадала в соседний день.

Теперь смещение определяется на момент создания каждого заказа. Например, `o_02357` создан 29 марта в `22:40:08 UTC`. В Берлине это уже 30 марта, но с постоянным зимним смещением сервис относил его к 29-му.

Причину нашёл в расчёте дат, затем проверил таймзону через API и сравнил распределение заказов с PostgreSQL `AT TIME ZONE`.

## Что ещё заметил

- `Math.floor(rub * 100)` иногда терял копейку: например, `1.13 * 100` даёт `112.99999999999999`. Исправил перевод в копейки через десятичный сдвиг. На данных API такая ошибка встречалась у 96 сумм оплаты.
- В API есть старые заказы без `amountPaid` и суммы в виде строк. Оба варианта поддерживаются.

## Допущения

- Если `amountPaid` отсутствует, заказ считается без скидки. Нулевая оплата допустима.
- День определяется по `createdAt`, учитываются только заказы со статусом `paid`, границы периода включительны.
- Настоящие доли копейки отбрасываются, как в исходном сервисе: `10.999 → 1099` копеек.

## Как проверял

- `npm run typecheck` — без ошибок.
- `npm test` — все 45 тестов прошли. Добавлены проверки скидок, копеек, миграции и переходов времени; сохранены проверки синхронизации, статусов и повторных вебхуков.
- На чистой БД выполнил `POST /sync`: 52 страницы, 5030 заказов, без невалидных записей.
- Затем отправил вебхуки командой из README: все 92 запроса получили HTTP 200.
- После этого запросил отчёт `c_7` за 27–31 марта и сохранил ответ в `result.json`. Все суммы совпали с отдельным SQL-расчётом по таймзоне клиента.

Проверка выполнялась с PostgreSQL 16 и приложенным образом `orders-mock:3`.

## Что доделал бы

- Перенёс бы проверку `updatedAt` в SQL, чтобы одновременные обновления одного заказа не могли перезаписать более свежую версию.
- Для старой заполненной БД отдельно загрузил бы исторические скидки: миграция считает прежние записи заказами без скидки, а повтор синхронизации с тем же `updatedAt` их не обновит.
